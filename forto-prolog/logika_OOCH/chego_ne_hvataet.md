# Часть I. Чего не хватает

## 1. Что уже есть в системе Ф0–Ф10

Базис K3: `¬` (Ф0), `∧` (Ф1), `∨` (вытекает из Ф1 через `¬` по де Моргану, но явно не зафиксирована).

Модальности Ł3: `L` (Ф4, необходимость), `M` (Ф5, возможность).

Охрана/согласие: `Ф2` (guard), `Ф3` (consensus), `Ф6` (запрет = ¬импликация K3).

Производные: `Ф7` (проверено), `Ф8` (восстановимо), `Ф9` (FDE-N, четвёртое значение).

Эпистемические: `Ф10` (epistemic lift, независимая экспертиза).

Итого: **10 функций + базисные `¬`, `∧`, `∨`**. Это достаточно богатая охранная подсистема, но **не полная логика проекта**.

## 2. Чего не хватает — структурно

Логика проекта должна уметь:
- **выводить** новые утверждения из имеющихся (нужна импликация),
- **формулировать общие** утверждения о всех объектах проекта (нужны кванторы),
- **описывать изменения** состояния проекта при действиях (нужна динамическая логика),
- **работать с замкнутым миром** в ряде контекстов (нужно отрицание по умолчанию),
- **моделировать время** проекта (нужны временные операторы),
- **агрегировать** мнение многих источников сверх простого согласия (нужно большинство/взвешивание).

Ниже — конкретные недостающие функции в порядке убывания критичности.

## 3. Недостающие функции (по приоритету)

### 3.1. **Импликация →** (критично)

**Что это.** Бинарная функция `A → B`, читаемая как «если A, то B». В K3: `max(¬A, B)`. В Ł3: `min(1, 1−A+B)`. У Брусенцова: `xy ∨ σx′y ∨ x′y′`.

**Почему критично.** Без положительной импликации невозможно:
- Цеплять рассуждения: «из A следует B; из B следует C; значит из A следует C»
- Формулировать правила как формулы: каждое правило ОЧ сейчас описывается на естественном языке + таблицей, а не как `前提 → следствие`
- Выполнять modus ponens: `A, A → B ⊢ B`

**Важный нюанс.** У нас есть **Ф6 (запрет) = ¬(A → B)**, то есть **отрицание** импликации. Но самой импликации нет. Это как если бы у нас был `¬A` без `A`. Система асимметрична.

**Что добавить.** Положительную импликацию. Рекомендация: **импликацию Брусенцова** `xy ∨ σx′y ∨ x′y′`, потому что:
- Она согласована с трактовкой `0` как «привходяще» (не «неизвестно»)
- Она отлична от K3 и Ł3, что соответствует 2-ступенчатой системе Брусенцова, которую мы уже используем
- Она позволяет корректно выразить «A → B» с третьим значением в посылке

Ввести как **Ф11 «импликация»**.

### 3.2. **Эквивалентность ↔** (высокий приоритет)

**Что это.** `(A → B) ∧ (B → A)`, или непосредственно как функция: `+1` если `A = B`, иначе `-1` (или `0` если кто-то неопределён).

**Почему нужно.** Для подстановок: «X то же, что Y» — без этого нельзя сказать, что две формулировки правила эквивалентны. Для рефакторинга: «новое правило ↔ старое правило». Для сверки: «источник A ↔ источник B».

**Что добавить.** **Ф12 «эквивалентность»**. Производна от Ф11, но как примитив удобна.

### 3.3. **Кванторы ∀ и ∃** (критично)

**Что это.** Универсальный и экзистенциальный кванторы: «для всех x выполняется P(x)» и «существует x, для которого P(x)».

**Почему критично.** Любое проектное правило уровня «все X должны Y» требует `∀`. Примеры:
- «Все коммиты должны быть подписаны» — `∀c. commit(c) → signed(c)`
- «Каждое правило ОЧ должно иметь проверку в коде» — `∀r. rule(r) → has_check(r)`
- «Существует тест для модуля M» — `∃t. test(t) ∧ covers(t, M)`

Без кванторов все правила ОЧ остаются **точечными**: они применяются к конкретным значениям, а не к классам объектов. Это делает логику подсистемой проверки значений, но не языком проекта.

**Что добавить.** Кванторную приставку к K3/Ł3/Брусенцов. Стандарт: K3 с кванторами = `K3∀` (Baaz, Fermüller). Ввести **Ф13∀ «все»** и **Ф14∃ «существует»**.

### 3.4. **Динамические операторы [α]φ и ⟨α⟩φ** (высокий приоритет)

**Что это.** Из пропозициональной динамической логики (PDL, Pratt 1976; Harel 1984):
- `[α]φ` — «после выполнения действия α, φ обязательно выполняется»
- `⟨α⟩φ` — «после выполнения действия α, возможно φ выполняется»

**Почему нужно.** Проект — это последовательность действий: commit, merge, deploy, review. Каждое действие меняет состояние. Чтобы сказать «после deploy сборка зелёная» — нужен `[deploy]green`. Чтобы сказать «после review можно мерджить» — `[review]mergeable`.

Текущая система Ф0–Ф10 статична: она описывает значения в один момент, а не их изменение.

**Что добавить.** Динамические операторы с трёхзначной семантикой: `[α]φ = L(φ_after_α)`, `⟨α⟩φ = M(φ_after_α)`. По сути, **Ф4 и Ф5 уже близки** к этим операторам, но не привязаны к действиям. Ввести **Ф15 [α]** и **Ф16 ⟨α⟩** как действие-связанные версии L и M.

### 3.5. **Отрицание по умолчанию (negation as failure)** (средний приоритет)

**Что это.** «not φ» — «φ не выводимо из текущей базы знаний». Отличается от `¬φ` (φ ложно). Это закрытый мир.

**Почему нужно.** В проекте часто нужно: «если для X нет теста, то X не протестирован» (а не «X протестирован ложно»). ОЧ-13 вводит «нет» для атомов, но не как оператор над любыми формулами.

**Что добавить.** **Ф17 «not»** — оператор default negation. Реализация: «not φ = если φ доказуемо, то -1; иначе +1». Это нарушает монотонность (добавление фактов может поменять результат) — но это и есть суть закрытого мира.

### 3.6. **Временные операторы □_F, ◇_F, until** (средний приоритет)

**Что это.** Из временной логики (LTL, Pnueli 1977):
- `□_F φ` — всегда в будущем φ
- `◇_F φ` — когда-нибудь в будущем φ
- `φ until ψ` — φ выполняется, пока не станет ψ

**Почему нужно.** Для проектных инвариантов: «всегда в будущем сборка зелёная после merge в main» — `□_F [merge]green`. Для SLA: «в течение 24 часов ошибка будет исправлена» — `◇_F(24h) fixed`.

**Что добавить.** **Ф18 □_F, Ф19 ◇_F** — временные аналоги L и M. Базовая идея: `□_F = «всегда в будущем L»`, `◇_F = «когда-нибудь M»`. Можно строить поверх Ф4, Ф5.

### 3.7. **Агрегация сверх согласия (большинство, взвешивание)** (низкий приоритет)

**Что это.** Ф3 (consensus) требует единогласия: «все источники согласны». Для проекта нужно:
- **Большинство** (2 из 3, k из n): «большинство тестов прошли»
- **Взвешенное большинство**: «эксперты с весом > w согласны»
- **Кворум**: «k из n согласны, при явке ≥ q»

**Почему нужно.** ОЧ-15 (спор вселенных) использует Ф3 — но это слишком строго: при одном несогласном всё рушится в 0. Для практики нужно «большинство».

**Что добавить.** **Ф20 «majority(k, n)»** — параметрическая функция. Не унарная/бинарная, а n-арная с порогом.

### 3.8. **Причинная импликация (counterfactual)** (низкий приоритет)

**Что это.** `A □→ B` — «если бы A было, то было бы B» (Lewis 1973, Stalnaker). Отличается от материальной импликации тем, что работает в ближайших возможных мирах, а не во всех.

**Почему нужно.** Для post-mortem анализа: «если бы мы добавили тест T, то баг B не прошёл бы в прод» — `T □→ ¬B`. Это причинное рассуждение, не материальная импликация.

**Что добавить.** **Ф21 «□→»** — каузальная контрфактическая импликация. Требует семантики возможных миров (Lewis), что усложняет систему.

## 4. Методологический вывод: от фрагмента к системе

Текущая Логика ОЧ с Ф0–Ф10 — это **фрагмент**, а не **логическая система**. Чтобы стать основной логикой проекта, нужно:

1. **Синтаксис**: формальное определение правильно построенных формул (well-formed formulas), включая переменные, предикаты, функции, кванторы, модальности, действия.

2. **Семантика**: модельная теория. Что значит «формула φ истинна в модели M»? Для K3/Ł3 — это трёхзначные оценки. Для динамической части — Kripke-структуры с переходами. Для временной — linear time flow.

3. **Система доказательств**: аксиомы + правила вывода. Не только таблицы истинности, но и натуральный вывод или исчисление секвенций. Это нужно для автоматической проверки.

4. **Кванторная приставка**: переход от пропозициональной логики к логике предикатов.

5. **Расширения**: динамическое, временное, эпистемическое (Ф10 уже намекает).

6. **Метатеория**: теоремы о полноте, непротиворечивости, разрешимости.

Без этих компонентов Логика ОЧ остаётся **табличной системой проверки значений** — полезной для конкретных правил, но не языком проекта.

**Статус:** закрыто. Описание достаточно для наших целей. Точные формулы в первоисточниках Słupecki 1936/1946 не сверялись, но это не влияет на выводы.

### 6.3. Имя Ф7 (проверено) — ЗАКРЫТО

Стандартного имени в литературе нет. Предложенное имя **«пост-функция проверки»** сохраняется. Разложение через J-операторы Россера—Тюркетта выписано в [itog_zaklyuchenie.md §3.6](./itog_zaklyuchenie.md).

**Статус:** закрыто. Имя рабочее, при необходимости заменяется.

### 6.4. Импликация Брусенцова — ЗАКРЫТО

Импликация `xy ∨ σx′y ∨ x′y′` сверена с K3-импликацией на 9 парах: **не совпадает**. Это согласуется с 2-ступенчатой системой Брусенцова: 1-я ступень — значения, 2-я — следование.

**Конкретная сверка:** при `A = -1` (всегда истинная посылка):
- K3: `max(¬A, B) = max(+1, B) = +1` (всегда истина)
- Брусенцов: `(-1)y ∨ σ(1)y ∨ (1)y = y ∨ σy ∨ y = y ∨ σy`. При `σ = 0`: `y ∨ 0 = max(y, 0)` = `[0, 0, +1]` для `y ∈ {-1, 0, +1}`.

K3 даёт «всегда истина» при истинной посылке; Брусенцов даёт значение следствия (с подъёмом `-1` к `0`). Это **разные импликации**.

**Статус:** закрыто. Импликация Брусенцова отличается от K3/Ł3, что ожидаемо.

### 6.5. ОЧ-13 (FDE-расширение) — ЧАСТИЧНО ЗАКРЫТО

Ф9 (FDE-N) построена как унарная функция на 4-значном домене `{нет, -1, 0, +1}`. Полная алгебра FDE-расширения (какие операции применяются к «нет» в композициях) не выписана.

**Статус:** частично закрыто. Эскиз есть, полной алгебры нет. Откладывается до отдельной работы.

## 8. ОЧ-20 — переформулировка как универсальное правило

### 8.1. Уточнение пользователя

ОЧ-20 касается **любого утверждения**, не специфического случая. Это меняет формализацию.

### 8.2. Новая формализация

ОЧ-20 как **универсальное правило над утверждениями**:

```
ОЧ-20: ∀z, y, e. 
  итоговое(z) ∧ эксперты_валидны(e) ∧ согласие(z, y) 
    → ¬корректировать(z)
```

где:
- `z` — любое утверждение, помеченное как «итоговое» (имеющее статус финального заключения)
- `y` — любое новое приходящее заключение
- `e` — признак валидности экспертов (источник нового заключения)
- `согласие(z, y) = Ф3(z, y)` (consensus)
- `эксперты_валидны(e) = L(e)` (Ф4, необходимость)
- `итоговое(z)` — мета-предикат: «z имеет статус итогового»

### 8.3. Тип правила

**ОЧ-20 — универсальное правило (universal rule)**, не функция значения и не просто правило устройства. Оно:

- **Кванторно**: применяется ко всем `(z, y, e)`, а не к конкретным значениям
- **Импликативно**: имеет форму `условие → следствие`
- **Использует предикаты**: `итоговое(z)`, `эксперты_валидны(e)` — это предикаты, не просто значения

### 8.4. Что это значит для системы

ОЧ-20 демонстрирует **конкретно и остро**, почему не хватает:
- **Импликации →** (Ф11) — правило требует `→` как основную связку
- **Универсального квантора ∀** (Ф13) — правило требует `∀z, y, e`
- **Предикатов** — правило использует `итоговое(z)`, `эксперты_валидны(e)`, не только функции значений

Это **прямая демонстрация** недостатков из Части I: ОЧ-20 **невозможно формализовать полностью** в рамках Ф0–Ф10, потому что для его записи нужны → и ∀, которых нет.

### 8.5. Функциональное ядро (если оставить только значения)

Если игнорировать кванторную часть и предикаты, то ядро правила как бинарной функции над значениями:

```
корректируемо(z, y) = ¬(Ф3(z, y) ∧ L(e))
```

при фиксации `e = +1` (типичный случай применения). Но это **потеря общности**: без `∀` правило применяется только к конкретным z, y, а не к классу утверждений.

### 8.6. Переклассификация

| Было | Стало |
|---|---|
| Правило устройства (как ОЧ-11) | **Универсальное правило** (требует ∀ и →) |

ОЧ-20 — это **первое правило в системе, явно требующее расширения**. Оно показывает границу текущей системы: Ф0–Ф10 хватает для проверки значений, но не для формулирования общих правил проекта.

### 8.7. Связь с Частью I

ОЧ-20 — **демонстрационный кейс** того, что нужно добавить:
- Без Ф11 (импликация) нельзя записать `условие → следствие`
- Без Ф13 (квантор ∀) нельзя сказать «для любого утверждения z»
- Без предикатов нельзя сказать `итоговое(z)`

**Это и есть ответ на Часть I:** конкретное правило ОЧ-20 показывает, каких функций не хватает. Если мы хотим формализовать все правила ОЧ как формулы, а не как таблицы значений — нужно добавить Ф11, Ф13, Ф14, и ввести предикаты.
